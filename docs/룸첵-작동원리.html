02

요청 한 건의 생애

실제로 req.status에 들어가는 값은 두 개뿐입니다. 나머지 상태처럼 보이는 것들은 전부 별도의 시각 도장(플래그)입니다. 이 구분을 알면 리스트가 왜 그렇게 나뉘는지 이해됩니다.

리스트 탭이 나뉘는 기준도 여기서 나옵니다. 확인자 화면에서는 부분 답변을 아직 처리 중으로 봅니다 — status==='requested'이거나, answered인데 answerComplete가 아직 아닌 것을 모두 대기로 묶습니다. 그래서 절반만 답한 요청이 목록에서 사라지지 않습니다.

03

요청 안의 구조

요청 한 건은 여러 개의 행(row)을 담고, 행 하나가 호텔 하나입니다. 그리고 행마다 두 종류의 곁가지가 붙습니다. 이 둘을 섞지 않는 것이 이 시스템에서 가장 중요한 구분입니다.

왜 배열을 나눴나 app.js 821

코드 주석에 이유가 그대로 적혀 있습니다. 추천을 추가 호텔과 한 배열에 섞으면 전체 개수가 함께 늘어나서, "2/2 완료"였던 요청이 추천을 하나 다는 순간 "2/3 답변 대기"로 되돌아갑니다. 그래서 별도 배열로 뺐습니다.

에이전트 화면에서는 추천 호텔에 삭제 버튼이 없습니다. 확인자가 제안한 것을 에이전트가 지우지 못하게 읽기 전용으로만 그립니다.

04

워크시트와 키

확인자가 채우는 답은 전부 req.ws라는 하나의 평평한 사전에 들어갑니다. 키 하나가 "어느 호텔의 어느 날짜"를 가리키고, 값은 그날의 상태와 요금입니다.

상태값은 네 가지입니다. 이 색은 앱 전체에서 예약된 색이라 버튼이나 탭에는 쓰지 않습니다.

어떤 호텔의 어떤 날짜가 S/O로 찍히면 호텔명|날짜 형태로 따로 기록해 둡니다. 나중에 다른 요청에서 같은 호텔·같은 날짜가 나오면 자동으로 마감이 미리 채워집니다. 확인자가 같은 곳에 두 번 전화하지 않게 하는 장치입니다.

입력은 두 단계로 할 수 있습니다. 위쪽 칸으로 전 날짜를 한 번에 바꾸거나, 날짜별로 하나씩 바꿉니다. 날짜마다 다르면 요약 칸에 혼합이 표시되고, 그 상태로는 저장되지 않습니다.

05

두 가지 조회 방식

입력 폼 맨 위의 다중호텔 / 다중호텔 숙박은 단순한 표시 차이가 아니라, 각 호텔의 첵인 날짜를 계산하는 방식을 바꿉니다.

06

답변 보내기와 진행률

확인자가 룸체크 답변 보내기를 누르면 다섯 가지가 한꺼번에 일어납니다.

/* app.js — #sendA 핸들러 */
buildWsFromDOM(req);   ← 화면의 모든 칸을 ws 로 다시 긁어 담는다
confirmChecks(req);    ← 다 채워진 추가 호텔을 confirmed 로
req.status = 'answered';
req.answerComplete = allDone(req);   ← 전부 채웠나?
recordFullbook(req);   ← 마감(S/O)을 다음 요청을 위해 기억

진행률 "답변 대기 n/m"의 분모는 기본 호텔 + 추가 호텔의 개수입니다. 추천 호텔은 세지 않습니다.

분모 — 몇 개를 알아봐야 하나

행 하나당 기본 호텔 1개에, 그 행에 달린 추가 호텔 개수를 더합니다. 호텔 2개짜리 요청에 각각 추가 호텔이 하나씩 붙으면 분모는 4입니다.

분자 — 몇 개가 끝났나

그 호텔의 모든 날짜에 상태가 들어와야 1로 셉니다. 2박 중 하루만 채우면 아직 0입니다.

부분 답변은 정식 기능입니다. 다 못 채워도 언제든 보낼 수 있고, 버튼에 부분 답변 보내기 (2/4)처럼 남은 개수가 표시됩니다. 나머지를 채워 다시 보내면 버튼이 룸체크 답변 업데이트로 바뀝니다.

직접 요청은 조금 다릅니다. 요청자가 에이전트를 거치지 않고 스스로 만든 요청은, 답변을 보내도 에이전트에게 바로 보이지 않습니다. 요청자가 따로 에이전트에게 넘기기를 눌러야 공개됩니다.

07

견적과 금액 노출

한 요청에 견적서를 여러 장 만들 수 있습니다. 구간마다 어느 호텔로 계산할지 골라서, 조합이 다른 견적을 나란히 뽑아 보내는 방식입니다.

견적 요청과 발송은 두 개의 도장으로 관리됩니다. 에이전트가 💬 견적 요청을 누르면 quoteRequested가 켜지고, 요청자가 견적을 보내면 quoteSent가 켜지면서 quoteRequested가 꺼집니다. 요청을 등록할 때 룸체크 + 견적요청을 고르면 처음부터 켜진 채로 시작합니다.

새 견적의 환율 기본값은 45입니다. 예전에 만들어진 견적은 그때 저장된 환율(40 등)을 그대로 유지합니다.

금액 가림은 화면 단에서만 이뤄집니다 확인 필요

원가를 숨기는 판단은 브라우저 안에서 ui.role을 보고 내립니다. 서버는 에이전트에게도 워크시트 전체를 그대로 내려보냅니다. 화면에 안 보일 뿐, 개발자 도구를 열면 값이 남아 있습니다.

지금 쓰는 방식(에이전트는 여행사 파트너)에서는 큰 문제가 아닐 수 있지만, 보안 경계가 아니라 표시 규칙이라는 점은 알고 계셔야 합니다. 서버에서 잘라 보내는 방식으로 바꿀 수 있습니다.

08

저장과 동기화

화면의 모든 편집은 먼저 브라우저에 저장되고, 잠시 뒤 서버로 밀려 올라갑니다. 그래서 잠깐 인터넷이 끊겨도 입력이 날아가지 않습니다.

내려받기에는 안전장치가 둘 더 있습니다. 입력칸에 커서가 있으면 새 내용을 적용하지 않고 넘어갑니다. 그리고 아직 못 보낸 편집이 있으면 내려받는 대신 먼저 올려보냅니다. 두 경우 모두 "내가 지금 치고 있는 것"이 이깁니다.

워크시트 합치기는 특히 중요합니다. 요청 전체를 통째로 덮으면, 오래된 화면을 열어둔 사람이 저장하는 순간 다른 사람이 채운 답이 사라집니다. 그래서 ws만은 키 하나 단위로 합칩니다 — 새로 온 값이 이기되, 보내지 않은 키는 서버 것을 그대로 둡니다.

요청 번호도 서버가 정합니다. 브라우저가 임시로 번호를 붙여 보내면 서버가 진짜 번호를 돌려주고, 브라우저가 그것으로 고쳐 씁니다. 두 사람이 동시에 등록해도 번호가 겹치지 않습니다. 일반 요청과 직접 요청은 번호 계열이 따로입니다.

10

확인이 필요한 것

이 문서를 쓰면서 코드를 훑다가 나온 것들입니다. 셋 다 실제로 돌려서 확인했습니다.

① 확인자가 남의 요청을 못 볼 수 있습니다 실측 확인

서버가 직원에게 요청을 내려줄 때 지역이 같은 것만 걸러 보냅니다. 그런데 요청에 지역을 넣는 코드가 어디에도 없습니다. 그 결과 직원은 자기가 만든 요청만 보게 됩니다.

테스트 계정을 만들어 직접 돌려봤습니다. 요청자가 요청 1건을 올린 뒤 각자 조회했을 때 — 요청자 본인은 1건, 확인자는 0건, 다른 요청자도 0건이었습니다. 요청 데이터에 지역을 손으로 넣어주자 같은 지역 직원에게만 1건이 보였습니다.

지금 운영이 돌아가고 있다면 직원 계정이 관리자 권한이거나 다른 경로가 있다는 뜻입니다. 실제 운영에서 확인자에게 요청이 정상적으로 보이는지 확인해 주세요. 안 보인다면 원인은 이것입니다. 고치는 방법은 두 가지 — 요청을 만들 때 지역을 함께 저장하거나, 지역 거르기를 없애는 것입니다.

② 부분 답변 알림의 개수가 항상 물음표입니다 코드 확인

부분 답변 알림은 {n}/{t}개 답변 형태로 쓰여 있는데, 서버가 읽는 _doneCount 값을 브라우저가 보내지 않습니다. 그래서 항상 ?/4처럼 나옵니다. 브라우저가 그 값을 함께 보내도록 한 줄 추가하면 됩니다.

③ 쓰이지 않는 잔재들 정리 대상

quoteAsk, quoteOnly, row.subOptions, req.checkerAddedHotels — 값이 만들어지지만 읽는 곳이 없거나, 읽지만 만드는 곳이 없습니다. 동작에는 영향이 없지만 코드를 읽을 때 혼란을 줍니다.

특히 checkerAddedHotels는 지금의 추천 호텔이 대체한 옛 경로로 보입니다. 지우기 전에 예전 데이터에 남아 있는지 확인이 필요합니다.

코드에서 직접 확인한 내용을 정리했습니다. 추측한 부분은 "확인이 필요한 것"에 따로 모았습니다. 기능을 바꾸면 이 문서도 함께 고쳐야 합니다.
